## Verdict

**1 MED + 7 LOW.** The v1.5.0 core claims hold under adversarial probing: AES-GCM-256 correctness (random 96-bit IVs — 2000/2000 unique — exact round-trip, no IV/key reuse path), graceful degradation on every crypto failure path probed, ample quota headroom, upgrade inheritance (nothing dropped; all legacy shapes readable), correct UTC→local time conversion, locale parity 35×6, and packaging-gate integrity. The MED is the **backup-import path**: `j.data` reaches `chrome.storage.local.set` with only an app-marker check, which concretely enables (a) a silent encryption downgrade to plaintext, (b) a persistent popup-log render break, and (c) type-confused settings/badge values. The LOWs are display/robustness/coverage items — most require a crafted import file (which itself requires a user file-pick + confirm) or a rare timing window.

### Finding details (evidence)

- **V4-1** — probe outputs: import predicate `verdict()` accepted all of `array data`, `proto key`, `null log entry`, `garbage cryptKey`, `type confusion` and rejected only `wrong app`/`null data`/`string data` (exact predicate from stats.js:182 executed). Consumer traces (exact expressions from content.js:398-401 / popup.js:113-114,125): `{enabled:"false"}` → enabled stays true; `{minDelayMs:"0"}` → 0 ms; `{clickCount:"1e9"}` → 1000000000; `{log:null}` → popup log len 0. Corrupt-key flush behaviour (exact lines content.js:303-306): with `cryptKeyRaw:"AAAA"` → `encryptCtx` null → entry keys remain `["at","kind","label","context"]` (plaintext). 9 corrupt `cryptKeyRaw` variants (bad base64, 3-byte, object, number, bool, 44×"A") all → `getKey: null | encryptCtx: null (plaintext fallback)`. 6 MB payload accepted, parsed in 8-12 ms. `background.js:41` reads `stats.byDay[day]` without coercion (a crafted object renders as a broken badge). Scoping: the handler cannot be reached by web content (no `externally_connectable`, file picker requires a user gesture); the attack requires the user to import a supplied file.
- **V4-2** — `chrome.storage.local.set` merges per top-level key (documented API semantics; the import test above writes only provided keys). The import handler runs on `chrome-extension://` — a different origin than the page, hence a different Web Locks partition — so `maa-record-v1` does not serialize it against content-script flushes.
- **V4-3** — probe: `await renderLog([null])` → `THREW TypeError: Cannot read properties of null (reading 'kind')`; `renderLog([5,"str",{}])` → no throw (primitives are tolerated; only `null` throws). The d7084da code at popup.js:58-60.
- **V4-4** — code path: `cryptKey` (content.js:257) and `popCryptKey` (popup.js:23) are module-level caches with no `storage.onChanged` invalidation for `cryptKeyRaw` (listener at content.js:404-410 handles only `enabled`/`minDelayMs`; popup.js:148 only refreshes). Consequence reasoned from the code; the popup-vs-content key-mismatch path matches the probe pattern for wrong-key decryption (`(unable to decrypt)`).
- **V4-5** — probe: two concurrent `getKey()` against one shared store with a delayed `set` → `stored==A? false | stored==B? true | A!=B? true`; the losing context's ciphertext `decryptable with stored key? false`. Serialized variant (lock-path equivalent): `B decrypts A ciphertext? true`. Web Locks origin partitioning is documented API behaviour.
- **V4-6** — grep over the d7084da e2e file; the suite asserts deep behaviour for the click paths (unchanged and still meaningful) but nothing for the v1.5 delta.
- **V4-7** — reasoned from the lock request without a signal/timeout; the never-fired-callback scenario was already noted as a rare class in v3.
- **V4-8** — probe table (exact localTime/localFull bodies): `'2026-10-09T07:51:59.000Z'` → `14:51:59` (UTC+7 host; correct), `'garbage'`/`''`/`{}`/`undefined` → `''`, `null` → `08:00:00` (+8 because the host Windows timezone carries the pre-1975 historical offset — `getTimezoneOffset()` = −480 for 1970 vs −420 now), `12345` → `08:00:12`, `'2026-10-09T14:00:00'` (no Z) → `14:00:00` (parsed as local).

## (b) Verified clean (executed unless noted)

1. **Crypto correctness.** Fresh `getKey` → 32-byte AES-GCM-256 key, stored as 44-char base64; `encryptCtx` emits `{iv, ct}` with a 16-char (12-byte) base64 IV; **2000/2000 IVs unique**; encrypt→stored-key→decrypt round-trip exact (`"Repository example/demo — approval text"`); cross-module round-trip (content.js encrypt → popup `decCtx`) returns the exact plaintext. Random 96-bit IVs with a per-install key — the 2³²-message birthday bound is unreachable at the 30 clicks/min cap.
2. **Crypto error paths (all probed).** `crypto.subtle` unavailable → `getKey` null → `encryptCtx` null → flush keeps plaintext ("never lose the record"); 9 corrupt/absent `cryptKeyRaw` shapes → same plaintext fallback; popup: missing/unloadable key → `'(encrypted)'`, wrong key/garbage ct → `'(unable to decrypt)'`, empty `iv`/`ct` falls through to the legacy branch. No throw escapes any path.
3. **Storage quota.** Worst-case encrypted entry (240-char context) = 448 B JSON → 50-entry cap ≈ **22.4 KB**, against 10 MB (`storage.local` ≥ Chrome 114) / 5 MB (110-113) — 2-3 orders of magnitude of headroom. Caps unchanged: log 50, byDay 400, byMonth 24, byTopic 100, queue 60.
4. **XSS — popup log** (`popup.js:57-68`): every interpolation (`at` title + text, `kind` class, kind label, label, context) passes `esc()` (& < > "); probe with `kind:'<img src=x>'`, `label:'"><b>bold</b>'`, `context:'<script>alert(1)</script> & "quotes"'` → fully entity-encoded; **real HTML parser**: only `b/div/span` tags, zero `on*` attributes.
5. **XSS — stats renderTopics** (`stats.js:90-102`): title attr replaces `"`→`&quot;`, text strips `[<>&]`; probe payloads `<img onerror>`, `"><svg onload>`, `&amp;lt;` → **real HTML parser**: only `div/span/i` tags, zero handlers, zero dangerous tags; payloads appear solely as inert attribute values / data. `renderChart` year labels filtered to `/^\d{4}$/` (probe: `'abc'`/`'<script>'` keys dropped; only `0000`,`2026` rendered); all values `num()`-coerced.
6. **Imported-shape coercion in render/aggregate paths.** `asObj()`-normalized buckets + `Number()` writes survive string/number/array/null `stats` shapes (probe: every case normalizes to 4 buckets, day write succeeds); `series()` on a string `byDay` → 0s, no throw; `Object.entries` on string/array/null `byTopic` → harmless entries; stats.js load/onChanged shape-guards hold. (The remaining unvalidated consumers are listed in V4-1.)
7. **renderSeq race** (`popup.js:52-56`): probe with a slow older render (150 ms key lookup) superseded by a fast newer one → the final DOM is the newer render; the stale one returns early. Guard works as designed.
8. **Local-time conversion.** Stored `at` is UTC ISO (`toISOString`); `localTime` uses local getters — probe on a UTC+7 host: `07:51:59Z` → `14:51:59`, hover `10/9/2026, 2:51:59 PM`. The epoch oddity is historical timezone data, not a code defect (V4-8 covers the non-string edge).
9. **Upgrade inheritance.** Legacy plaintext entries render via `decCtx`'s fallback (probe: `'legacy plaintext context'` displayed); mixed legacy+encrypted logs map cleanly; the flush path only prepends and slices — it never strips `context` from old entries and never deletes unknown keys; legacy stats shapes (`byDay` missing/other) normalize safely; `schemaVersion` is written per flush (`content.js:315`) and **read nowhere** (grep: 2 occurrences, both writes) — it cannot break inheritance; there is no path that drops legacy data on upgrade. Note (by design, per CHANGELOG): legacy entries are **not re-encrypted** — old plaintext contexts remain at rest until they age out of the 50-entry window.
10. **Flush serialization.** Web Locks path holds the lock across the whole get→(encrypt)→set (verified by reading; the lock-path-equivalent probe shows consistent key use), with the unlocked fallback and the `started` guard; queue caps at 60; `resolve()` is reached on every error path found (getKey/encryptCtx swallow internally; set is try/caught); `clickFlushing` resets in `finally`.
11. **Guards & regex (re-run).** ON_MUSE table: `muse.ai`/`www.muse.ai`/`evil.muse.ai`/`MUSE.AI`/`muse.ai:8443` pass, `xmuse.ai`/`muse.ai.evil.com` fail, trailing-dot host fails (fail-closed); MUSE_URL_RE accepts ports, rejects lookalikes/trailing-dot; no ReDoS: 80k-char URL in 4 ms, ON_MUSE 10k calls in 1 ms, `extractTopic` 10k×240-char adversarial in 31 ms. No new page-facing regexes were added by v1.5.
12. **Permissions / network / remote code / sinks.** Manifest: `["storage","alarms"]` only, hosts `https://muse.ai/*` + `https://*.muse.ai/*`, no `web_accessible_resources`, no `externally_connectable`, `all_frames:true` unchanged; grep across `extension/`: no `eval`, `new Function`, `fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, `localStorage`, `storage.sync`, `postMessage`, `importScripts`, `insertAdjacentHTML`, `document.write`; the only `innerHTML` sinks are the five reviewed (popup.js:57,93; stats.js:87,94,98).
13. **Packaging gates.** `build.mjs` items list covers the extension tree and the full-tree set-equality guard (exits 3/4) is present — simulated on the d7084da tree: 18 disk files == 18 expected entries, 0 missing/0 extra. `verify-zip.py` derives the zip name from `manifest.json` (v3-8 fixed) and byte-compares zip vs disk; executed read-only it **correctly detected live drift** during this review (exit 1, 3 mismatches) once the in-flight wave diverged from the built zip — the gate works. The `dist` zip itself corresponds to a later tree than d7084da (Housekeeping).
14. **e2e core assertions.** The click-path assertions (11 expected, 0 forbidden, dedup counts, order, locksProbe, statsCheck, statsPage) are unchanged from v1.4 and still falsifiable for their targets; the v1.5 gap is V4-6.

## (d) NOT_VERIFIED

- **Browser execution of anything.** By instruction the e2e suite was not run and no Chrome was driven: Web Locks contention behaviour, real `chrome.storage.local` quota rejection (import >quota → alert path), and Chromium's internal handling of stored keys literally named `__proto__` (JS-level semantics probed: `JSON.parse` yields an own property, no global pollution, `Object.assign` into a fresh object *does* re-route it through the prototype setter — but no code path in the extension performs such an assign; impact bounded to that object). The import handler was validated by executing its exact predicate, not in a browser.
- **HTML parsing semantics** were validated with Python's `html.parser` (spec-faithful for the tokenizer states involved), not with Chromium; the entity-in-attribute reasoning matches v3 and the parser output.
- **The d7084da-era zip.** `dist/` now holds a zip rebuilt from a later tree (see Housekeeping); byte-compare vs d7084da blobs: 15/18 exact, and the 3 differences (`content.js`, `popup.html`, `popup.js`) are post-d7084da polish edits (zip == the 311f006-era disk, verified). The d7084da-time zip was not captured, so "18/18 byte-verified" (commit message) is unconfirmed for the exact commit.
- **V4-7's stall scenario** — no fault injection; reasoned from code.
- **Popup visual rendering / the in-flight a11y wave** — reviewed revision is d7084da; the later CSS/a11y edits are outside this review.
